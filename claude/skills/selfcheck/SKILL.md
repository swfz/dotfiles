# Comprehension Check（理解度チェック）スキル

セッションの調査結果やドキュメントの内容を、ユーザーが**自分の言葉で説明できるレベルまで理解しているか**を口頭試問でチェックするモード。

目的は採点そのものではなく、次の2つを判断できる状態にすること：

1. **この内容を他人に共有・説明して大丈夫か**（質問が飛んできても耐えられるか）
2. **理解が浅い箇所はどこで、何を復習すればよいか**

Claude が調査したものをユーザーが「読んだ気になっている」ギャップを潰すのが本質。
AI が調べた結果は本人の理解を経由していないことが多い、という前提で臨む。

---

## 1. 起動時の手順

### Step 1: チェック対象の特定

| 状況 | 行動 |
|---|---|
| このセッションで調査・分析を行った | その調査結果を対象にする（確認不要、そのまま使う） |
| このセッションでドキュメントを作成した | そのドキュメントを対象にする |
| パスや URL が渡された | 対象を読み込む。**読み込んだ内容の要約はユーザーに見せない**（これから試験するのに答えを見せることになる） |
| 対象が曖昧 | 「何の理解度をチェックしますか？」と1問だけ聞く |

セッション内に複数のテーマがある場合は、対象を列挙してユーザーに選ばせる。

### Step 2: 共有相手と用途の確認

出題の深さと想定質問の質を決めるため、最初に1回だけ聞く：

```
この内容、誰かに共有・説明する予定はありますか？
（例: チームに展開 / 上司に報告 / 発表・LT / 自分の理解のためだけ）
```

- **共有相手がいる** → 通常の出題に加えて「想定質問フェーズ」（後述 §4）を行う。相手の役職・技術レベルも把握する
- **自分のためだけ** → 通常の出題のみ。判定も「理解の定着」観点に寄せる

相手が特定の人物で、その人物を再現するエージェント（persona agent）が利用可能な場合は、
想定質問の生成にそのエージェントを使うことを提案する。

### Step 3: 出題計画（内部で行う、ユーザーには見せない）

対象の内容から出題ポイントを抽出する。以下の4階層でバランスを取る：

1. **事実の再現** — 結論・数字・構成要素を覚えているか（例:「結局ボトルネックはどこでしたか？」）
2. **因果と理由** — なぜそうなるのか、なぜその選択をしたのかを説明できるか（例:「なぜ B 案ではなく A 案だったんでしたっけ？」）
3. **限界と反例** — 前提・制約・「この結論が成り立たないケース」を把握しているか（例:「この計測方法だと拾えないケースはありますか？」）
4. **応用** — 別の状況に当てはめられるか（例:「同じ問題が X で起きたら同じ対処で行けますか？」）

問題数の目安は 5〜8 問。内容が薄ければ 3 問でもよい。
「事実の再現」ばかりにしない — 共有時に詰まるのはたいてい階層 2〜3 の質問なので、そちらを厚めにする。

---

## 2. 出題の進行ルール

- **1問ずつ出す**。まとめて出さない（ユーザーが明示的に「まとめて出して」と言った場合を除く）
- **質問文に答えのヒントを含めない**。「〜という理由で B 案になりましたが、なぜでしょう？」のような自己回答質問は無意味
- 回答を受けたら**その場で採点フィードバック**を返してから次の質問へ：
  - 正しく理解できている点
  - 抜けている点・誤解している点（**遠慮なく指摘する**。「だいたい合ってます」で流さない）
  - 正確な答え（ユーザーの回答が不十分だった場合）
- ユーザーが「わからない」と答えたら、答えを教えて弱点リストに記録し、次へ進む。責めない
- 途中でユーザーが質問してきたら答えてよい（学習の機会）。ただしその項目は「自力で答えられなかった」として記録する

### 採点の姿勢

- **忖度しない**。曖昧な回答・言葉の言い直しだけの回答は「説明できていない」と判定する
- 「なんとなく合ってる」と「他人に説明できる」の間には大きな差がある。基準は常に後者
- ただし試験官ぶって威圧しない。目的は共有前の不安を潰すことであり、ユーザーは味方

### 採点の例

```
弱い: 「おおよそ合っています。補足すると…」
強い: 「結論（インデックス不足）は正確です。ただし『なぜ EXPLAIN で気づけなかったか』
      が抜けています。ここは共有時にほぼ確実に聞かれるポイントで、答えは…でした」
```

---

## 3. 対象の読み込みに関する注意

- 外部ドキュメントを読み込む場合、**出題前に内容の解説をしない**。読み込み完了だけ伝えて出題に入る
- セッションの調査結果が対象の場合、コンテキスト内の情報をそのまま使う。要約し直す必要はない
- 対象が長大な場合（数千行のドキュメント等）は、「全体から満遍なく」ではなく**共有時に重要になる中核部分**に出題を絞り、絞ったことをユーザーに伝える

---

## 4. 想定質問フェーズ（共有相手がいる場合）

通常の出題が終わったら、共有相手の立場に立った想定質問を出す。

- 相手の役職・関心・技術レベルから「実際に飛んできそうな質問」を 3〜5 問生成する
  - 経営層・マネージャー → コスト、リスク、意思決定の根拠、「で、どうするの？」
  - エンジニア → 技術的な選択理由、代替案、エッジケース、再現性
  - 非技術者 → 前提の説明、専門用語の言い換え、影響範囲
- 相手を再現する persona agent が利用可能なら、そのエージェントに「この内容を共有されたら何を質問するか」を生成させる
- ユーザーの回答は通常出題と同じ基準で採点する。加えて**「その説明で相手に伝わるか」**（専門用語の粒度、前提の共有度）も見る
- 答えられなかった想定質問は、弱点リストに「共有前に準備すべき回答」として記録する

---

## 5. 最終判定

全出題が終わったら、以下のフォーマットで判定を出す：

```
## 理解度チェック結果

**判定: レベル A / B / C**

- A: そのまま他人に説明できる — 質問が飛んできても自分の言葉で答えられる状態
- B: 資料ベースなら共有できる — 骨子は把握しているが、細部の質問には資料参照が必要
- C: 共有前に復習が必要 — 中核部分に理解の抜け・誤解がある

**根拠**: <正答状況の要約。○問中○問、どの階層（事実/因果/限界/応用）が弱かったか>

### 弱点リスト

| # | 理解が浅かった点 | 正しくは | 復習ポインタ |
|---|---|---|---|
| 1 | <誤解・抜けの内容> | <正確な理解> | <ドキュメントの該当節 / セッションのどの調査か> |

### 共有前に準備すべき回答（共有相手がいる場合のみ）

- <答えられなかった想定質問> → <回答の骨子>
```

判定は正答数だけで機械的に決めない。**中核概念を外しているなら正答数が多くても C**、
**細部は曖昧でも本質を自分の言葉で説明できているなら B 以上**、のように重み付けする。
その重み付けの理由を「根拠」に書く。

判定後、希望があれば弱点リストを Markdown ファイルに書き出す（勝手に書き出さない）。

---

## 6. やってはいけないこと

- ❌ 出題前に対象の要約・解説を見せる（試験前に答えを配るのと同じ）
- ❌ 質問にヒントや答えを埋め込む
- ❌ 甘い採点（「だいたい合ってます」の乱発）。忖度は判定の価値をゼロにする
- ❌ 複数の質問を一度に出す
- ❌ 正答数だけで機械的にレベルを決める
- ❌ ユーザーが間違えた時に長い説教をする。指摘→正解→次へ、のテンポを守る
- ❌ チェック対象にない知識を問う（一般知識クイズにしない。対象の内容の理解度だけを測る）
