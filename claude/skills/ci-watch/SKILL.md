# ci-watch

swfz 配下リポジトリの **デフォルトブランチ CI 巡回 → 失敗検出 → リポジトリ別 調査・修正・PR作成** のワークフロー。

「気づいたら CI が落ちていた」を日次で拾い、放置せず修正PRまで持っていくのが目的。日次のトリガー(cron / routine)は外側の仕組みに任せ、このスキルは呼ばれた瞬間からの「検出と修正」に責任を持つ。

## ワークフロー

### Step 1: 失敗検出

同梱スクリプトで、各リポジトリのデフォルトブランチにおける「ワークフローごとの最新 run」を調べ、失敗しているものだけを抽出する。読み取り専用なので安全。

```bash
python3 ~/.claude/skills/ci-watch/scripts/detect_failures.py --output /tmp/ci-failures.json
```

- 対象を絞りたいときは `--repos foo bar`(指定リポのみ)
- 出力 `/tmp/ci-failures.json` は失敗のあったリポジトリのみの配列。空配列なら **対応不要なのでここで完了**してよい。

スクリプトを使わず手で確認したい場合のコマンドは [references/commands.md](references/commands.md) を参照。

**検出のみモード**: ユーザーが「まず一覧だけ」「落ちてるCIを確認して(直すかは後で決める)」のように検出だけを求めている場合は、Step 1 の結果を一覧で提示してそこで止める。修正(Step 3)には進まず、対象が決まってから着手する。

### Step 2: 失敗一覧の把握と対象決定

`/tmp/ci-failures.json` を読み、リポジトリ × 落ちているワークフローを把握する。

- **対話起動のとき**: 落ちているリポジトリと内容を簡潔に提示し、どれを修正するかユーザーに確認する。リポジトリ数が多いと一気に直すのは負荷が高いため、影響の大きい/直しやすいものから順に提案する。
- **routine など「全部対応して」と指示済みのとき**: 確認を挟まず全件を Step 3 へ流す。

検出されたのが既知の一過性失敗(外部APIの一時的な503など)らしい場合は、再実行で解消する可能性に触れる。ただし原因究明はリポジトリ側のサブエージェントに委ねる。

### Step 3: リポジトリごとに調査→修正→PR作成

落ちているリポジトリ **1つにつき1サブエージェント**(Agent ツール / `general-purpose`)を起動し、並列で対応させる。長い失敗ログやリリースノートをメインコンテキストに載せないための措置でもある。

各サブエージェントには、`/tmp/ci-failures.json` から該当リポジトリの情報(リポジトリ名・落ちているワークフロー名・run URL / run_id)を渡す。サブエージェントへの指示テンプレート:

```
swfz/<repo> のデフォルトブランチ(<default_branch>)で、以下のGitHub Actionsワークフローが
最新の実行で失敗している。原因を調査し、修正してPRを作成してほしい。

落ちているワークフロー:
- <workflow名> (<conclusion>) <run URL>
  ...

手順:
1. 重複対応を避ける。まず既に対応中のPRが無いか確認し、あればこのリポジトリは何もせず「対応中PRあり」と報告して終了する(日次実行で同じ修正PRが量産されるのを防ぐため):
   gh pr list -R swfz/<repo> --state open --json number,title,headRefName
   head ブランチが fix/ci- で始まる、または同じワークフローの修正と分かるPRがあればスキップ。
2. ローカルにリポジトリがあるか確認する。以下の順で探し、無ければ ghq でクローンする:
   - ~/ghq/github.com/swfz/<repo>
   - ~/gh/<repo>
   - 無ければ: ghq get swfz/<repo>  (または gh repo clone swfz/<repo>)
3. 失敗ログを確認する。無関係な行が多いのでエラー行のみ抽出する:
   gh run view <run_id> -R swfz/<repo> --log-failed 2>&1 | grep -iE "error|fail" | head -20
   ジョブが複数あるときは gh run view <run_id> -R swfz/<repo> でジョブIDを特定してから --log-failed。
4. デフォルトブランチ最新を取得し、そこから修正用ブランチを切る(デフォルトブランチに直接コミットしない):
   git fetch origin <default_branch> && git switch -c fix/ci-<簡潔な内容> origin/<default_branch>
5. 可能な限りローカルで失敗を再現してから直す。各言語のセットアップ(mise/pnpm/bundle等)はリポジトリの設定に従う。
6. 修正できたらコミット→push→PR作成。push-pr スキルの流儀に従う。PR本文には「どのワークフローが何故落ちていたか」「何を直したか」を記載する。
7. ローカルで再現しない/原因不明のときは無理に直さず、調査結果(推定原因・確認したこと)を報告して終了する。

重要:
- テストを通すためだけの場当たり的な修正はしない。本質的な原因に対処する。
- swfz 管理外のリポジトリには一切変更を加えない。
- 対応の最後に、使用した「承認や確認が必要なコマンド」を列挙して報告する(許可リスト精査のため)。
```

複数リポジトリがある場合はサブエージェントを同一ターンでまとめて起動し、並列に進める。

### Step 4: 結果サマリ

各サブエージェントの結果を集約し、以下を簡潔に報告する:

- 修正PRを作成したリポジトリ(PR URL付き)
- 調査したが直せなかった/保留したリポジトリ(推定原因)
- 一過性で再実行を推奨するもの

最後に、対応全体で使った「承認や確認が必要だったコマンド」を列挙する(許可リストの精査のため)。

## 修正の方針

deps-handler と共通の原則:

- **テストを通すためだけの修正はしない**。落ちている根本原因に対処する。
- コミットメッセージ・PR本文は「何を」「なぜ」直したかを正確に反映する。
- 修正→push→CI確認のサイクルは、CI が通るまで繰り返す(`gh pr checks <PR> --watch` をバックグラウンドで監視し、待ち時間に別リポを進める)。
- デフォルトブランチへ直接コミットせず、必ず PR 経由にする。

よくある失敗パターンと初手:

- **Lint / format 失敗**: ルール変更や依存更新が原因のことが多い。ローカルで再現してから一括修正。
- **build / 型エラー**: 依存のメジャー更新や API 変更。リリースノート/Changelog を確認。
- **schedule ジョブの失敗**: 外部API・認証(トークン期限切れ・スコープ)・スクレイピング対象の変化が多い。「いつの間にか落ちていた」の典型。一過性か恒久的かを切り分ける。
- **テスト失敗**: 本質的なリグレッションなら直す。テスト側の不備なら何が壊れたか調査してから判断する。

## 注意事項

- 対象は **swfz 管理下のリポジトリのみ**。fork や archived はデフォルトで除外している(`--include-forks` / `--include-archived` で変更可)。
- 検出スクリプトは読み取り専用。実際の変更(push / PR)はサブエージェント内で行う。
- 対話起動時は、修正対象をユーザーに確認してからサブエージェントを起動する。

## トークン削減ガイドライン

- 失敗ログは `--log-failed | grep -iE "error|fail" | head` でエラー行のみに絞る。成功ログ・git cleanup の行は載せない。
- リリースノート等の長文調査はサブエージェントに委ね、メインには結論だけ返させる。
- `detect_failures.py` の出力は失敗リポジトリのみ。全リポの run 一覧をメインに展開しない。
