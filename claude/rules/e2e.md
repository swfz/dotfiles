# E2E Rules

リポジトリ固有のヘルパー名や遷移の仕方は、そのリポジトリの CLAUDE.md に書く。ここには特定のリポジトリに依存しない原則だけを置く。

## ページの開き方

- 初期化が重いアプリ(wasm・大きなデータの読み込み・ログインなど)では、テストごとに `page.goto` でページを開き直さない
  - ワーカー単位でページを使い回し、SPA 内の遷移で画面の state だけを作り直すヘルパーを用意する
  - 重い初期化をルーターより外側(Provider など)で持っていれば、遷移しても再初期化されない
- 初回ロード・Loading 表示・`page.route` でレスポンスを差し替えるテストなど、初期化そのものを確かめるテストだけはフルリロードで書く
- 使い回し用のヘルパーを入れたら、state がリセットされることと、重い初期化が再実行されないこと(例: wasm のリクエストが出ない)を確かめるテストも書く

## テスト間の状態を持ち越さない

ページを使い回すときは、各テストの後で次のものを元に戻す。

- `page.route` で足した route(`page.unrouteAll`)
- `page.on` で足したリスナー(`pageerror` / `console` / `request` など)
- `setViewportSize` で変えたビューポート
- マウス位置(`page.mouse.move(0, 0)`)
  - マウスが前のテストと同じ座標に残っていると `hover()` で mousemove が発生せず、ツールチップなどが更新されないことがある

## 待ち方

- `waitForTimeout` で固定時間待たない。要素や状態の変化を条件にして待つ
- 再描画中に位置が動く要素へのホバーやクリックは、期待した結果になるまで `expect(async () => { ... }).toPass()` でやり直す
- `retries` でフレーキーを隠さない。落ちたら原因を直す

## CI での実行

- `workers` を明示する(例: `workers: process.env.CI ? 2 : undefined`)
  - 既定は CPU 数の半分で、プライベートリポジトリの GitHub ホストランナー(2 vCPU)では 1 になり直列実行になる
- CI では dev サーバではなくビルド済みの成果物(`vite preview` など)に当てる。dev サーバは初回アクセスごとにモジュール変換が走って遅い
- ワークフロー側の扱いは github-actions のルール(実行コスト)を参照

## 変更後の確認

テストの並列度やページの使い回し方を変えたら、通常の実行に加えて次の条件でも通ることを確かめる。

- `--repeat-each=3`: テスト間の状態漏れを炙り出す
- `--workers=1`: CI と同じ直列実行での順序依存を炙り出す
- 落ちたテストがあれば、そのファイルだけ `--repeat-each=20` で再現・修正確認する
